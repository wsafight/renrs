# 阅读、渲染和回滚优化

测量于 2026-09-06。这是 Ren'Py 对比之后的 P0-P2 迭代。[性能测量](PERFORMANCE.md) 中的历史结果是
另一次测量。项目尚未发布：该次测量的存档使用容器 v2 和快照 v7；当前代码写入 v8 并兼容读取 v7。
内容更新仅在活动位置可通过显式 ID 或 alias 解析时恢复；这不会迁移更旧快照格式。

后续的 [原生字体内存优化](FONT_MEMORY.md) 把测得的 RenRS 空闲 RSS 从 359.3 降到 127.5 MiB。
下面的原生表描述更早的字体实现；后续文档含当前内存结果。

## 已完成工作

- [x] P0：缓存原生素材，并在输入、剧情变化、动画、资源完成、重载和存储响应时失效。静态场景在
  普通 housekeeping 唤醒时不再重绘。仅存档缩略图仍走存储 worker。
- [x] P0：在唤醒之间阻塞 macOS 事件循环。worker 定时器请求更新，并通过安全 objc2 API 发送 Cocoa
  事件。动画用 16.667 ms 节奏；housekeeping 用 100 ms。绝对截止时间防止定时器睡过头累积；长时间
  停顿会重置节奏而不爆发。
- [x] P0：Web 已读历史每两秒批量写入、去重 ID，并在存档、进入后台和离开页面时刷新。存储失败保留
  dirty 状态以便重试并显示提示。
- [x] P0：Web Unicode 打字机、完成后再推进、模态/后台暂停、保存的揭示进度、揭示后自动延迟和跳过
  已读。富文本和注音预留排版；已有 NVL 文本保持可见。
- [x] P1：缓存展平后的自定义界面布局和可见存档列表；重载或槽位变化后重建/失效。渲染保留共享舞台
  状态，而不是每次绘制都克隆。
- [x] P1：跨 jump、条件备选、选项、call 和 return 预测资源，不执行脚本表达式。遍历上限 256 个位置、
  16 层调用和 16 张独立图片。
- [x] P1：在运行时、快照和回滚检查点之间共享变量表、舞台状态和嵌套列表/记录。变更用 copy-on-write；
  失败的界面编辑事务式恢复先前状态。
- [x] P2：增加可重复的 Ren'Py/RenRS 夹具、原生测量模式、外部进程采样、截图检查和保留二进制的状态对比。

场景缓存在全部原生目标上工作，但阻塞事件循环唤醒只在 macOS 启用并验证。Windows/Linux 保持普通
事件循环。即使在 macOS，housekeeping/输入唤醒仍会提交缓存纹理；零次场景重绘不等于零 GPU 工作或
零 CPU 活动。

## 方法

硬件：Apple M3 Pro、arm64、macOS 26.5.2、120 Hz 内建显示。实际执行的官方 SDK 是 Ren'Py
8.5.3.26051504，来自 `renpy-8.5.3-sdk.zip`。其 SHA-256 对照
[官方校验和](https://www.renpy.org/dl/8.5.3/checksums.txt)：

```text
ff57648f9c04f27e381c48af6d8e3ee3cdec296bed4d3831f47f09b0a71b505e
```

本地 `references/renpy` 源码检出不是被测 SDK 版本。RenRS 是 release 构建。输出记录其二进制
SHA-256；工作区没有提交基线，因此这些是按二进制标识的本地测量。

两份夹具使用相同的背景、角色和 NotoSansSC 字体，资源哈希在 `manifest.json`。逻辑/窗口尺寸
1280x720，Retina 截图 2560x1440。440x650 角色从 x=84 开始。空闲保持同一段已完全揭示的对白；
运动在 30 秒内线性移到 x=484。无音频。每次运行在资源就绪后预热两秒，再测八秒。每个场景跑三次，
交替引擎顺序。引擎串行运行，中间没有构建或其他测试。

CPU 是外部 `ps` 累计进程 CPU 增量除以采样墙钟时间；100% 是一个逻辑核。RSS 是该窗口内观察到的
最高进程采样，不是 GPU 内存或系统总分配。轮询请求 250 ms 间隔；实际采样时间戳保留。首末采样落在
八秒窗口内，因此采样时长更短。跨越报告创建的采样丢弃。截图和 PNG 编码发生在测量报告之后，再过
0.5 秒拍第二张。检查器要求运动至少 32 种采样颜色和 500 个变化像素。

这些是可比较的资源和剧情场景，不是相同的渲染工作负载：

- RenRS 渲染 1280x720 场景目标再缩放到 Retina drawable；Ren'Py 渲染到 2560x1440 drawable。因此文字栅格不同。
- RenRS 保留正常工具栏；Ren'Py 夹具是最小 say 界面。
- 两者都请求 60 Hz，但 macOS GL swap interval 请求在这块屏上不能可靠限制 Ren'Py。实际绘制率有报告。RenRS 唤醒次数和 Ren'Py 绘制调用是不同的仪器点，不能互换为 CPU 时间或端到端显示帧测量。
- 三次短跑不能建立冷启动、电池、GPU、大型商业项目或跨平台优势。就绪包含预热，不是冷启动基准。

## 原生结果

三次运行的中位数，括号内为完整观察范围。十二次运行都通过非空白检查；空闲验证帧相同，每对运动
变化超过 112,000 像素。进程采样覆盖每次运行 7.68-7.80 秒。

| 场景 / 引擎 | CPU（一个核的%） | 峰值采样 RSS (MiB) | 约 8 秒内的场景/绘制调用 |
| --- | ---: | ---: | ---: |
| 空闲 RenRS | 1.30 (1.29-1.30) | 359.3 (359.3-700.7) | 0 |
| 空闲 Ren'Py | 2.06 (1.95-2.20) | 241.2 (239.2-242.1) | 50 (49-50) |
| 运动 RenRS | 7.61 (7.54-7.64) | 353.5 (353.4-353.6) | 481 (481-482) |
| 运动 Ren'Py | 12.46 (12.19-13.71) | 237.2 (235.9-243.8) | 960 (952-960) |

RenRS 空闲时避免场景重绘，运动时维持大约每秒 60 次场景更新。其运动唤醒 p50 为 16.48-16.63 ms，
p95 为 19.10-20.02 ms。Ren'Py 尽管请求 60 Hz，实际约每秒绘制 119-120 次。这张 CPU 表不能建立
渲染效率或 FPS 优势，因为绘制率和内部栅格分辨率都不同。

RenRS 在两个场景都用更多进程内存。一次空闲运行在采样开始时已有 700.7 MiB 峰值；保留该异常，
原因尚未隔离。两秒预热不能保证分配已经稳定。较大峰值不是截图分配采样，因为截图只在报告之后开始，
跨边界采样被丢弃。

产物：`target/engine-comparison-verified/results-1788694206504/summary.json`、各 `*.process.json`
采样和成对的 `*.start.png` / `*.end.png`。截图名指测量后的验证，不是窗口边界。更早的试验目录排除：
它们用过先前的定时或采样逻辑，包括截图分配跨过边界的运行。

```text

39ed6c6c1f99abe3cceb6e92f0ed021c94a2fcdf1f8ee7d82f797b8da37a45a8
```

## 共享状态结果

这比较 P1 前后的 RenRS，不是 Ren'Py。夹具构建 16 个列表、每个约 64 条约 128 字节字符串的嵌套
物品栏，每句对白改一个标量，并填满 256 项回滚窗口。两个二进制都执行 818 条指令 / 401 次交互。
结果是三次分开运行的中位数，交替二进制顺序；命令的 `3` 参数只重复编译。

| 操作 | 改前 | 改后 | 观察 |
| --- | ---: | ---: | --- |
| 执行路线 | 11.575 ms | 0.905 ms | 少 92.2% 时间 |
| 快照加 JSON 序列化 | 23.919 ms | 16.351 ms | 少 31.6% 时间 |
| 从内存快照恢复 | 11.610 ms | 0.281 ms | 少 97.6% 时间 |
| 持久存档 | 174.763 ms | 157.905 ms | 这些运行少 9.6%；磁盘时间会变 |
| 未缓存列出六个存档 | 2384.392 ms | 2393.155 ms | 无改进 |
| 快照 JSON | 34,773,179 字节 | 34,773,179 字节 | 体积未减 |

恢复时间不含磁盘读取和 JSON 解析。反序列化不会跨检查点重建共享身份，序列化 JSON 仍复制其内容。
大型未缓存存档列表仍然昂贵；缓存可见列表减少重复工作，但不解决第一次完整读取。

产物：`target/engine-comparison-verified/state-results-1788694170096/`。

## 复现

从仓库根目录，官方 SDK 解压到下面路径：

```sh
cargo build --offline --release --bin renrs-bench --example inspect_frames
cargo build --offline --release -p renrs-player --bin renrs
node scripts/generate-engine-comparison.mjs target/my-engine-comparison
node scripts/compare-engines.mjs target/my-engine-comparison target/renpy-sdk/renpy-8.5.3-sdk 3
node scripts/compare-state.mjs target/my-engine-comparison
```

使用新的夹具目录。原生测量需要交互桌面会话；不要向基准窗口输入。进程采样器使用 POSIX `ps`，
在 macOS 上验证过。状态对比另外需要保留的 `target/renrs-bench-before-p1` 可执行文件；当前未跟踪
的工作区无法从基线提交重建它。每个结果目录包含单独运行和摘要，原生测量还有原始进程采样和验证截图。

## 验证

- 完整 Rust workspace/all-target 测试、源码行数检查、格式化和严格 Clippy（`-D warnings`）通过。覆盖包括 COW 隔离、事务失败、预测遍历和定时器漂移/停顿行为。

- 最终原生自定义界面/存读档冒烟通过，17 张非空白截图：`target/smoke-optimization-cadence/report.json`。其偏截图的帧时间和 RSS 不用作性能证据。
